# 单 API Key 模型与上下文实测报告

## 结论

- 仅使用 `reg/get_apikey.txt` 第一枚 Key，SHA-256 指纹前缀：`061f8e614740`；第二枚 Key 未使用。
- 当前项目网关发现 **53** 个模型；最小生成调用 **53/53 成功**。
- 平均延迟 `4.05s`，P95 `5.62s`。
- 认证模型目录的 `context_length` 分为 128K、192K、200K、256K、500K、512K、1M、1.048M 和 1.05M 档。
- 硬边界抽测发现目录标称 `131,072` 的 `muse-glimmer-30b` 实际成功处理 **523,004 prompt tokens**，真实路由至少约 523K，接近 524,288；目录值不是当前路由的硬限制。

## 方法

1. 用第一枚 Key 启动当前仓库 `todo2api`，本地网关只配置一个上游账号。
2. 从本地 `/v1/models` 读取认证上游目录。
3. 对每个模型调用 `/v1/chat/completions`，固定提示为 `Reply with exactly OK.`；HTTP 200 且非空才算通过。
4. 对目录中最小上下文模型递增构造输入，并以响应 `usage.prompt_tokens` 作为实测 token 数。
5. 压测达到单 Key 的 2 USD 信用上限后停止，没有切换第二枚 Key。

## 上下文解释

- “目录上下文”来自该 Key 认证后的 `GET /api/v1/models`，是当前服务声明值。
- “边界实测”才表示当前路由真正接收并完成推理的 prompt token 数。
- `muse-glimmer-30b` 的声明值与实测明显不一致，因此不能把其余模型的目录值无条件当作硬上限。
- 本轮可以确认所有 53 个模型可调用；除 `muse-glimmer-30b` 外，其余模型的硬上限仍以认证目录值作为可用配置值。
